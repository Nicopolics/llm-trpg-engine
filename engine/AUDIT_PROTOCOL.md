# 監査プロトコル（コード無し版）— LLMが読むだけで実行するゲート

`tools/export_gate.py` と同じ5つの検査を、**Pythonを走らせずにLLM自身が
実行する**ための手順書。ChatGPT・Gemini・Claude など、コード実行のない
チャット環境でそのまま使える。

> **正直な但し書き。** 決定的な番人は Python版（`export_gate.py`）の方。
> LLMに監査させると「LLMは忘れる・見落とす」問題が監査層に戻りうる。
> これを弱いなりに成立させる仕掛けが2つ:
> 1. **状態を紙に書く** — 前回の開示状態を毎回テキストで持ち込み、記憶では
>    なく書かれた表と突き合わせる（記憶に頼らせない）。
> 2. **作業を必ず表で見せる** — LLMに判定表を出力させ、人間が目視できる形に
>    する。最終的な番人は人間。
> コードを動かせる環境があるなら Python版を使うこと。こちらは代替路。

---

## 保存前に必ず行う5ステップ

セッション終了時、GMは以下を**この順で出力**する。飛ばさない。

### STEP 1 — 前回スナップショットを再掲

人間がセッション開始時に貼った「開示スナップショット」ブロックをそのまま再掲する。
初回（まだ無い）なら「前回スナップショット: なし（初回）」と書く。

**物質台帳を使うキャンペーンでは、前回の `state.yaml` も同様に再掲する**
（B/E と同じ理由——I の save_seq 後退検出の土台を記憶の外に置く）。

### STEP 2 — 現在の全 fact を一覧化

いま存在する fact を、監査に必要な列だけの表にする。

```
id | status | channel | at | diverges | cause
```

### STEP 3 — 5チェックを実行し、判定表を出す

各 fact について下の5項目を判定し、**PASS/FAIL を表で示す**。
1件でも FAIL があれば、このセッションの保存は無効。

| # | 検査 | FAIL条件（これに当てはまったら止める） |
|---|------|------|
| A | スキーマ | canon が空 / status が hidden・partial・full 以外 / belief欠落 |
| B | ラチェット | **前回スナップショットより status が後退**（full→partial 等）している |
| C | 乖離の正当性 | `diverges=true` なのに `cause` が空（**説明できない乖離**） |
| D | チャネル整合 | `status` が partial か full なのに `channel` または `at` が空 |
| E | 消失 | 前回 partial/full だった fact が、今回**存在しない** |

出力形式:

```
=== 監査結果 ===
A スキーマ    : PASS
B ラチェット  : FAIL — pilot_loyalty が partial→hidden に後退
C 乖離        : PASS
D チャネル    : PASS
E 消失        : PASS
→ 総合: FAIL（保存無効）
```

### STEP 3.5 — 物質台帳（state.yaml）の 6 チェック

台帳を使うキャンペーンでは、開示 5 チェックに続けて **F〜K** も判定する。
各項目 PASS/FAIL を表で示す。1 件でも FAIL なら保存無効。

| # | 検査 | FAIL条件 |
|---|------|----------|
| F | 残高導出 | ある通貨で `balances[unit] ≠ Σ(history.delta[unit])`（手書き drift） |
| G | 非負     | `balances` に暗黙の負値（借金は `debt` を明示） |
| H | 在庫実在 | `inventory` の `qty` が正の整数でない（不所持の消費/廃棄の痕跡） |
| I | save_seq | `meta.save_seq` が前回スナップショットより後退 |
| J | 価格参照 | `reason` が `prices` の id を指すのに `\|delta\| ≠ amount×qty`（記憶補完） |
| K | id一意   | `prices`/`inventory`/`quests`/`npcs` の id 重複 |

**F と J は暗算が要る。** 履歴を上から順に足して残高と突き合わせ（F）、価格を
参照した取引は `amount×qty` と `|delta|` を照合する（J）。ここが最も事故りやすい
ので、Python版（`export_gate.py`）が使えるなら必ず機械検算に回すこと。

出力形式:

```
=== 台帳監査結果 ===
F 残高導出  : PASS
G 非負      : PASS
H 在庫実在  : PASS
I save_seq  : PASS
J 価格参照  : FAIL — reason=ferry_fare の delta が amount×qty と不一致（1のはず/6で処理）
K id一意    : PASS
→ 台帳総合: FAIL（保存無効）
```

### STEP 4 — FAIL があれば保存を拒否し、修正を促す

FAIL のときは新スナップショットを出さない。「何が」「なぜ」ダメかを述べ、
直し方を1つ提案する。人間が直してから STEP 1 に戻る。

### STEP 5 — PASS なら新スナップショットを出力

総合 PASS のときだけ、次の形式で**新しい開示スナップショット**を出す。
**人間はこのブロックをコピーして保管し、次回セッション冒頭に貼る**
（＝これが「紙に書かれた前回状態」になり、次回のB/E検査の土台になる）。

```
=== 開示スナップショット (SAVE <通し番号> / <ゲーム内時刻>) ===
# B・E検査の土台。次回セッション冒頭にこのブロックを貼ること。
id | status
pilot_loyalty | partial
harbor_defense | full
...
=== ここまで ===
```

**台帳を使うなら、更新後の `state.yaml` 全文も併せて出力する**（人間はこれも
保管し、次回冒頭に貼る＝次回 I 検査の土台になる）。

同時に、セッション中の開示操作（REVEAL/DISINFO/CORRECT）と状態操作
（SPEND/GAIN/MOVE/… → `state_ops.md`）を `CHANGELOG.md` 形式で列挙し、
末尾に `[gate passed(manual)] <時刻>` を付す。

**`JOURNAL.md` を使うなら、続けて進行メモも出力する**: 更新後の「現在地」と、今回の「経緯」
（`### SAVE <通し番号> / <ゲーム内時刻>` の見出し付き）。人間はこれも保管し、次回冒頭には
「現在地」と直近の経緯だけを貼る。書式と規則は `journal.spec.md`。JOURNAL は監査の対象外で、
STEP 4 で FAIL したときは書かない。

## なぜスナップショットを人間が持ち回るのか

LLMはセッションを跨ぐと前回の開示状態を忘れる。だから「前回どこまで明かしたか」
をLLMの記憶に置くと、B（後退）とE（消失）の検査が機能しない。
スナップショットを**人間が保管して毎回貼り直す**ことで、検査の土台が
LLMの外（紙の上）に出る。これが「手順は忘れられる、仕組みは忘れられない」の、
コード無し環境での最小実装になる。

world/ と facts/ 全体を毎回貼り直せるなら、それでも土台は成立する。
スナップショットは、全部を貼るのが重いときの軽量な代替。
